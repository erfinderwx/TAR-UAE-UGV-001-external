# 文档检查与总览工具

维护方式沿用项目统一文档样板。`build_index.py`及两个工作流由样板复用，适配TAR-UGV目录、summary校验和上海时区；补充相对链接、命名与附件检查。

- `python tools/build_index.py`：更新首页标记区和 `docs/INDEX.md`。
- `python tools/build_index.py --check`：检查文件头。
- `python tools/check_docs.py`：检查文档、图片链接、受管理文档命名、50 MB 上限和来源原件校验值。
- `python tools/check_changes.py`：全量检查正文版本／日期格式、定稿确认字段、AI 指引一致性和来源登记。
- `python tools/check_changes.py --base origin/main`：再比较当前工作区与指定 Git 基线，检查修改必须升版、日期不倒退、既有原件与登记身份不能改写或删除。先读取工作区状态，再安全获取远程状态；未提交的新正文也检查。
- `python -m unittest discover -s tools -p 'test_check_changes.py' -v`：在临时 Git 仓库运行正反例，不修改本项目资料。
- 依赖：Python 3.12、PyYAML、Git。检查器不联网读取审批记录，不需要上传凭据。

## 变更纪律

受管理正文为 `docs/` 下的 Markdown，排除 README、INDEX、模板及 `assets/` 原件。版本格式为 `v主版本.次版本`，可再加补丁／修订号；修改后必须数值递增，例如同一天 `v1.0` → `v1.1` 合法，`v1.0` → `v1.0.0` 不算升版。Windows 正文的 CRLF／LF 换行转换本身不算内容修订；原件仍严格按字节校验。`updated` 必须为有效的 `YYYY-MM-DD`，不得早于基线日期。文件名仍保持稳定。

正文标为“定稿”时须填写 `approved_by`、`approved_on`、`approval_ref`。后者使用可公开的确认记录 HTTPS 链接，或从仓库根目录起算的现存相对文件路径（可带锚点）。占位姓名和无效日期不通过。字段可追溯不代表审批真实、技术正确或已获发布许可；人员须核实确认记录确实覆盖该版本。Tag、公开范围和发布清单仍按仓库规则核对。内部审批证据留在内部受控记录，公开文件只引用已允许公开的确认记录。

来源清单可以增加新原件、补充描述与规范正文关联，但已有条目的 `id / path / original_filename / sha256 / bytes` 与对应原件必须保留。新收到的修订稿应使用新来源路径／编号；不能同时修改原件和清单哈希来覆盖证据。默认全量检查只验证当前一致性，只有提供 `--base` 才能发现这种历史改写。无法解析基线时检查失败，不会静默跳过。

`AGENTS.md` 和 `CLAUDE.md` 一旦存在，须同时存在且内容完全一致。

## 自动执行与边界

全部 PR 和 main 推送均执行检查，不再按目录过滤，因此仅修改附件、图片或治理文件也会运行。PR 使用只读仓库权限；main 的索引任务在相同检查通过后生成 README 与文档总览。索引任务串行运行，若 main 在运行中前进，普通推送会停止，等待最新一次任务处理；不会强推或覆盖他人提交。

PR 比较目标分支基线，main 推送比较该次推送之前的提交；首次推送和手动运行执行全量检查。自动检查是 CI 结果，是否能阻止直接提交取决于仓库保护设置，不能把检查工作流等同于强制分支保护。

检查器不判断评审意见是否合理、工程型号是否兼容、测试是否通过，也不把 PR 合并当作工程定稿。HTML／MD／图片一致性、原始资料解释、外部链接权限与对外发布范围仍需实际审阅。不得将内部资料整库同步至本公开仓库。

没有配置定时发布、邮件通知或跨仓库同步。
